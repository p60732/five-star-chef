# 遊戲自動修正規格（防踩雷清單）

來源：
- 霧海群島（mist-isle）m3-1 至 m3-34 的踩雷紀錄
- 五星大主廚（five-star-chef）M0 單機原型的 30 次提交（2026-10-21～22），其中 25 次是試玩回饋後的修正

目的：下一個遊戲開發時，改動前後自動檢查，把問題擋在提交前；需求不清楚時先確認，不要先做再改回來。

---

## 一、踩過的雷

### A. 霧海群島（介面、存檔、經濟）

| 類型 | 實際發生的情況 | 怎麼發現的 | 防範方式 |
|---|---|---|---|
| 名稱衝突 | 新增的 `dexHTML` 與既有的材料圖鑑同名，後者被覆蓋 | 人工比對 | 提交前掃描頂層宣告名稱是否重複 |
| 串接錯誤 | `';+advDexHTML()` 讓呼叫永遠到不了，語法檢查通過 | 功能測試 | 新功能必須有「呼叫後有結果」的測試 |
| 範圍刪除誤刪 | 多行範圍替換時把 `seenN`、`NEED2` 一起刪掉 | 載入測試 | 檢查 diff 的 `-` 行只能是預期要刪的 |
| 存檔覆寫 | 離開頁面時的存檔把 `savedAt` 蓋掉 | 離線測試 | 測試時關閉自動存檔；存檔時間以最後一次實際寫入為準 |
| 視覺遮擋 | 眨眼的眼皮蓋住睫毛；眨眼層被表情圖壓住 | 截圖 | 疊層順序要有截圖檢查 |
| 結果看不到 | 寶箱結果寫在捲動區上方 | 玩家回報 | 結果顯示在玩家目前看的位置 |
| 跑馬燈被切掉 | 長提示在滾完前被清掉 | 玩家回報 | 自動換行，顯示時間依字數計算 |
| 超出邊界 | 小地圖的木樁伸到海裡 | 玩家截圖 | 裝飾物座標檢查是否在允許範圍內 |
| 狀態殘留 | 「再抽」用全域 `mode` 判斷來源，信物和金幣混淆 | 測試 | 來源用參數傳入 |
| 舊存檔缺欄位 | 新增欄位後舊存檔載入出錯 | 設計時預見 | 新欄位都要有載入預設值，用舊存檔測試 |
| 測試環境問題 | 測試頁放錯資料夾，圖片全破 | 截圖 | 測試頁要讀得到同一份素材 |
| 測試檔汙染 | 測試截圖寫進專案根目錄 | 提交前 | 測試檔放 scratchpad，提交前看 `git status` |
| 實機差異 | iPhone 上的問題無頭瀏覽器重現不了 | 玩家回報 | 實機問題需要裝置、步驟、截圖 |

### B. 五星大主廚（即時操作、物理、多人規則）

| 類型 | 實際發生的情況 | 怎麼發現的 | 防範方式 |
|---|---|---|---|
| 畫面大小與碰撞不一致 | 食材模型放大到 2.3 倍（半徑約 0.45 格），碰撞半徑還是 0.32，停在檯面邊時模型陷進櫃子 | 玩家截圖 | 碰撞半徑由模型大小推出，或加測試：模型半徑 ≤ 碰撞半徑 |
| 推離函式方向反了 | 把東西「放到人前面一個身位」時點落在檯面裡，推離函式往格子中心推，東西卡進檯面 | 玩家回報 | 任何「直接設定位置」都要先確認在可走格子裡；推離只往外推 |
| 回歸測試沒重現問題 | 第一次寫的測試站位旁邊沒有工作台、或斜著推，舊版也會過 | 拿舊版跑測試 | 回歸測試必須先在舊版失敗、新版通過，才算數 |
| 用巧合當測試前提 | 很多測試用「鍋子不收生番茄」代表「放不下」，規則改成鍋子什麼都收後 5 項一起壞 | 改規則時 | 測試要明確建出狀態（例如把鍋子裝滿），不要借用別的規則 |
| 測試座標寫死 | 1-2 的砧板寫成 (3,1)，實際在 (4,1) | 測試失敗 | 測試用「找第一個某種格子」的小工具取座標 |
| 寫檔變數重用 | 同一段腳本裡 `p` 先指向規則檔、後面又拿來寫測試，把測試內容寫進規則檔 | 測試載入失敗 | 每次寫檔前印出路徑；提交前看 `git diff --stat`，改動行數異常就停 |
| 畫面狀態沒重設 | 「轉正」寫在「隱藏影子」的 else 後面，東西飛過一次就再也不會轉正 | 玩家回報 | 每幀要重設的視覺狀態不要接在 else 鏈裡；加「進入狀態 → 離開狀態後歸零」的檢查 |
| `[hidden]` 失效 | 暫停視窗的 CSS 寫了 `display:flex`，蓋過 `hidden`，一開局就擋住畫面 | 截圖 | 樣式表一律加 `[hidden]{display:none!important}` |
| 拿掉功能沒拿乾淨 | 拿掉「矮牆」後，編輯器草稿、說明、測試還留著 | 玩家回報 | 拿掉功能時搜尋所有層：規則、畫面、編輯器、關卡檢查、關卡資料、文件、測試 |
| 瀏覽器草稿不會跟著更新 | 關卡編輯器的草稿存在 localStorage，內建關卡改了玩家看不到 | 預見 | 內建資料改版時提醒「還原內建」；草稿帶版本號，舊版本提示 |
| 近似判斷在斜角出錯 | 「越過檯面」只看水平或垂直主軸，斜著丟判斷錯 | 玩家回報 | 物理判斷沿實際方向逐步檢查，不用主軸近似 |
| 防呆規則互相打架 | 「身邊有工作台就不准放地上」後來擋住正常放盤子 | 玩家回報 | 每條防呆寫明是為了擋哪個情況，並測兩邊：該擋的擋、不該擋的放行 |
| 數值單人太難 | 單人訂單 22 秒一張、切菜要按住 2 秒 | 試玩 | 所有手感數字集中在一個設定區，人數難度表另外放 |
| 訂單出現斷斷續續 | 訂單滿了計時器照樣重設，出完菜要空等 30 秒 | 試玩 | 「補位」邏輯：滿了就等空位立刻補，清空時最多等 N 秒 |
| 位置容錯太嚴 | 正對才拿得到，玩家覺得菜不好拿 | 試玩 | 互動找身邊 8 格最可能的目標，並畫出目標框 |
| 守恆被打破的風險 | 盤子、鍋子、食材在拿、丟、洗、疊之間轉手 | 每步測試 | 每個 tick 檢查守恆：盤子總數、鍋子總數、食材數、分數 |
| 用詞誤會 | 玩家說「矮牆」，指的是壓矮後的隔牆，我以為是新做的矮牆格子，來回改了三次 | 玩家第三次回報 | 玩家用的名詞對不上程式裡的東西時，先用截圖確認指的是哪一個 |
| 改了又改回 | 「落地滾上檯面」做完玩家覺得奇怪，整個撤回 | 玩家回報 | 手感類改動先描述效果或做成開關，確認再寫死 |
| 提交說明寫錯 | 說「各做突變確認會紅」，其實有一條拿掉也不會紅 | 自己複查 | 提交說明只寫實際跑過的結果 |
| 沙盒擋外部資源 | 無頭瀏覽器載不到 CDN 的 Three.js，畫面一片空白 | 煙霧測試 | 測試時把外部腳本攔截改用本機檔案 |

## 二、提交前自動檢查（每次改動都要跑）

### 通用
1. **語法**：每個 JS 檔與頁面內 `<script>` 都要 `node --check`。
2. **名稱衝突**：掃描頂層 `function`、`const`、`let`、`var`，有重複就失敗。
3. **改動量檢查**：`git diff --stat` 裡任何檔案的改動行數超過預期（例如規則檔一次變動數百行）就停下來看。
4. **刪除審查**：diff 的 `-` 行只能是預期要改的；頂層宣告被刪要在提交說明寫明。
5. **開機煙霧測試**：無頭瀏覽器載入頁面，攔截外部腳本改用本機檔案，不得有 `pageerror`。
6. **提交閘門**：`git status` 只有預期檔案；沒有測試檔、截圖、暫存檔。

### 規則（遊戲邏輯）
7. **規則是純函式**：`step(state, inputs, dt)` 不修改傳入狀態、不讀時間、不碰畫面；有測試檢查「跑完傳入的 state 不變」。
8. **可重現**：同樣的種子與輸入跑兩次，結果完全一樣。
9. **守恆**：每個 tick 檢查會轉手的東西總數不變（盤子、鍋子、食材）、分數＝加分－扣分、每個東西只在一個地方。
10. **閉環測試**：每條主流程從頭跑到回到起點（例如拿 → 切 → 煮 → 出餐 → 盤子回來 → 洗 → 回到原位）。
11. **突變測試**：每條新規則故意改壞一次，測試必須失敗；不會失敗的就補測試，或在說明寫明它只是保險。
12. **回歸測試先紅後綠**：修 bug 時，新測試要先用舊版跑、確認失敗，再用新版確認通過。

### 關卡
13. **1 到 N 人逐一檢查**：每個人數都能走到必要工作台、各區之間傳得了東西。
14. **成對工作台**：例如水槽旁要有晾盤架；有回收口就要有水槽。
15. **改關卡後重跑關卡檢查**；新放的格子不能讓別的工作台變成走不到。

### 畫面與物理
16. **大小一致**：每種物件的畫面半徑 ≤ 碰撞半徑（用模型大小 × 縮放算出來比較）。
17. **位置合法**：所有「直接設定位置」的地方（放下、落地、擠開、彈回）之後，位置都在可走格子裡，且離牆至少一個半徑。
18. **狀態歸零**：飛行、滑行、搬運等暫時狀態結束後，旋轉、影子、進度條都回到預設。
19. **截圖檢查**：改到畫面的版本，在 390×844 截一張主要畫面，看遮擋、溢出、元件被蓋住。
20. **用狀態掛鉤驗證操作**：頁面提供除錯用的狀態讀取（例如 `window.FSC_DEBUG.state()`），自動測試用它確認「按了之後狀態真的變了」，不只看畫面沒報錯。

## 三、自動修正的範圍

可以自動修的，只限機械性、結果可預期的項目：
- 舊存檔缺欄位 → 補預設值。
- 數值越界 → 夾在合法範圍內（貨幣不為負、星數不超過上限）。
- 裝飾物或地上物件超出範圍、陷進牆或檯面 → 移回最近的合法位置。
- 樣式表缺 `[hidden]{display:none!important}` → 補上。

以下不自動修，擋下並回報：
- 名稱衝突、語法錯誤、整段刪除、改動量異常的 diff。
- 守恆被打破、閉環測試失敗。
- 任何會改變玩家進度、經濟平衡、手感數值或劇情的修正。

## 四、回報與需求確認

**玩家回報 bug** 需要：裝置與瀏覽器、操作步驟、截圖或錄影。缺一項先問，不猜原因。

**玩家要求改玩法時**：
1. 玩家用的名詞對不上程式裡的東西（例如「矮牆」可能是兩種東西），先用截圖或關卡座標確認。
2. 手感類改動（推多遠、會不會滾上桌、要不要自動瞄準），先用一句話描述效果；能做成設定開關的就做成開關，玩家確認後再定。
3. 改動會推翻之前的規則時，說清楚「之前為什麼這樣做、改了之後哪些情況會不同」。
4. 改了又要改回：用 `git revert` 整個撤回，不要手動東拆西拆。

## 五、開發規則（寫進專案規範）

- 不用多行範圍刪除程式碼；用「舊字串必須恰好出現一次」的替換，失敗就停。
- 寫檔的腳本裡，每個要寫的檔案用不同的變數名，寫之前印出路徑。
- 新的存檔欄位必須有載入預設值。
- 來源或狀態用參數傳遞，不用全域旗標猜。
- 所有手感與難度數字集中在一個設定區（例如 `CFG`、人數難度表），程式其他地方不寫死數字。
- 規則只寫一份，伺服器與畫面共用；畫面不自己判斷規則。
- 每條防呆規則旁邊寫註解：擋的是哪個情況。
- 測試用小工具取座標與建狀態，不借用其他規則的副作用。
- 開發用的後門（例如 `?dev=1` 發放金幣）上線前移除，列入上線清單；除錯用的狀態讀取保持唯讀。
- 測試腳本與截圖放 scratchpad，不進專案。
- 每次提交說明寫清楚：改了什麼、為什麼（引用玩家回饋原話）、測試結果；只寫實際跑過的結果。
